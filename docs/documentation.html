Track 1

Getting started & installation

One static binary, no config files, no cluster, no DBA. Pick an install path, start it, and you have the engine, the dashboards, the CeQL textbook, the REST API and the MCP server. Default HTTP port is 7771; the gateway's data plane defaults to :8080; data is one file (centauri.log, or ~/.config/Centauri/ / %APPDATA%\Centauri for centauri desktop).

Install on Linux / macOS — the one-liner#

install.sh detects Linux or Darwin and amd64 or arm64, downloads the matching release binary from GitHub Releases, and moves it to /usr/local/bin/centauri (using sudo only if that directory isn't writable). It fetches one static file and nothing else goes through a shell. Pin a release with CENTAURI_VERSION.

curl -fsSL https://centauridb.com/install.sh | sh
# pin a version
CENTAURI_VERSION=v0.3.0 curl -fsSL https://centauridb.com/install.sh | sh
# then
centauri desktop

Manual fallback: download centauri-linux-amd64, centauri-linux-arm64, centauri-darwin-amd64 or centauri-darwin-arm64 from the latest release and chmod +x it.

Install on Windows — installer or zip#

centauri-windows-setup.exe (built from installer/centauri.iss) puts centauri.exe and the .bat launchers in C:\Program Files\Centauri, adds a Start Menu entry that runs centauri desktop, and an optional desktop icon. Your facts live in %APPDATA%\Centauri, so uninstalling never touches data. Prefer portable? Unzip centauri-windows-amd64.zip anywhere and double-click run-centauri.bat.

https://github.com/aniljacobv-lab/centauri/releases/latest
  centauri-windows-setup.exe   → installer (Start Menu + shortcut)
  centauri-windows-amd64.zip   → unzip, double-click run-centauri.bat

On first run you're asked Set up your private local AI now? [Y/n]. Press Enter and Centauri installs Ollama if needed and downloads the model trio once; when it's done you'll see ai: your private AI is ready — ASK and SEARCH now run on local models, nothing leaves this machine.

Docker & docker-compose#

The Dockerfile is a two-stage build (golang:1.22-alpine → alpine:3.20) with the binary at /usr/local/bin/centauri, VOLUME /data, port 7771, and ENTRYPOINT ["centauri"], so any subcommand works as the command. The admin token comes from CENTAURI_TOKEN.

docker build -t centauri .
docker run -p 7771:7771 -v centauri-data:/data -e CENTAURI_TOKEN=secret centauri

services:

    volumes: ["centauri-data:/data"]
    ports: ["127.0.0.1:7771:7771"]   # localhost only; your proxy provides TLS
    restart: unless-stopped
volumes:
  centauri-data:

Five-minute quickstart — the HTTP API#

Writes go to POST /v1/append with an events array; each event names a subject, a facet, a type (OBSERVED, CORRECTION…), a provenance (SYSTEM_FEED, HUMAN_ENTRY, SCAN_VERIFIED, AI_INFERRED), a confidence and a value. Reads are plain GETs; /v1/query runs CeQL as ?q= or a JSON body. With -token set, add Authorization: Bearer to every call.

centauri serve -data my.log -token secret
curl -X POST localhost:7771/v1/append -H 'content-type: application/json' \
  -H 'Authorization: Bearer secret' -d '{
  "events": [
    {"subject":"sku:TEA-NEW","facet":"source","type":"OBSERVED",
     "provenance":"HUMAN_ENTRY","confidence":1,
     "value":{"price_cents":899,"category":"beverage","name":"loose leaf tea"}}
  ]
}'
curl 'localhost:7771/v1/stats'
curl 'localhost:7771/v1/context?subject=item:100001/store:4001'
curl 'localhost:7771/v1/asof?subject=item:100001/store:4001&at=2026-03-15'
curl 'localhost:7771/v1/pending?facet=pdt&older_than_days=21'
curl 'localhost:7771/v1/disagreements?field=price_cents'
curl -N 'localhost:7771/v1/watch?facet=pdt'
curl 'localhost:7771/v1/query?q=FACTS%20OF%20sku:TEA-NEW'

Five-minute quickstart — CLI & shell#

centauri shell is a psql-style CeQL REPL (it takes the writer lock so it won't race a running server): \d lists subjects; \schemas, \stats, \slots, \timing, \x, \format are the meta commands; \q quits. centauri export -q "…" prints a query as table / csv / jsonl / json / yaml / plain. centauri demo seed builds a curated multi-domain demo.log; demo clear removes it — the only "erase" in the product, and it only touches that disposable file.

centauri seed -data my.log -skus 2000 -stores 8 -changes 5
centauri export -data my.log -q "FACTS OF item:*" -format table
centauri shell -data my.log
centauri> FACTS OF toy:robot
centauri> \d
centauri> \timing
centauri> \q

Track 2

Querying — CeQL, SQL, Postgres wire & hybrid search

CeQL is the native language: time, cause and trust are syntax. A read-only SQL SELECT subset and a PostgreSQL wire listener exist for people and tools that think in SQL; a plain-English helper exists for everyone else. The full textbook is the CeQL Book — this track is the working reference.

The mental model: subjects, facts, facets#

No tables, rows or documents. A subject is anything facts can be about (item:100001/store:4001, toy:robot), created the first time a fact mentions it. A fact is an immutable statement with two clocks (effective time — when it became true; recorded time — when the database learned it), a provenance, a confidence and causal links. A facet is which system's view the fact belongs to (source, register, pdt, shelf). A new fact on the same subject + facet supersedes the old one, which is kept forever: current state is just the newest layer of history. Name subjects like paths so wildcards behave like directories.

FACTS OF toy:robot                              -- what's true now
PUT toy:robot SET price_cents=500, color='silver'
HISTORY OF toy:robot                            -- the whole story

Reading: FACTS, projection, WHERE, paging#

Patterns use *. List fields to narrow output, including the built-in rank column for stable row numbers when paging. WHERE sees your value fields and the metadata (subject, facet, type, provenance, namespace, trust, effective, recorded, pending, superseded). Operators: = != > >= < <= IN LIKE MATCHES EXISTS AND OR NOT ( ); dotted paths reach nested values. String-equality filters use an automatic per-field secondary index; EXPLAIN shows when it's probed.

FACTS [fields] OF subject-pattern
  [FACET f] [AS OF t] [AS KNOWN AT t] [WHERE expr]
  [GROUP BY key] [ORDER BY key [DESC]] [LIMIT n] [OFFSET n]
  [WHY [DEPTH n]]
FACTS subject, price_cents, trust OF item:*/store:4001 ORDER BY price_cents DESC LIMIT 10
FACTS rank, subject, price_cents OF item:*/store:4001 ORDER BY price_cents DESC LIMIT 10 OFFSET 10
FACTS OF item:*/store:4001 WHERE trust >= 0.8 AND price_cents > 700
FACTS OF acme:* WHERE namespace = 'acme'

Writing: PUT, CORRECT, RETIRE#

Insert and update are the same act: PUT appends a fact that supersedes the prior one. CORRECT is the same but typed CORRECTION. RETIRE supersedes with {retired: true} — there is no DELETE, on purpose. PUT accepts FACET, TYPE, EFFECTIVE (future- or back-dated), CONFIDENCE, SCHEMA (validated write), PROVENANCE and REF (lineage). CeQL SET takes scalars only; nested arrays/maps go through POST /v1/append or an SDK. Writes need the admin token, an OIDC token with the write scope, or a scoped token granted write.

PUT toy:robot SET price_cents=450, color='red'
PUT toy:robot SET price_cents=400 EFFECTIVE '2026-07-01'   -- future-dated
CORRECT toy:robot SET price_cents=445                     -- typed CORRECTION
RETIRE toy:robot                                          -- supersedes with {retired: true}
RETIRE route:api FACET config                             -- retire one facet

Time travel: AS OF and AS KNOWN AT#

Two clauses because every fact has two clocks. AS OF t asks what was true at t. AS KNOWN AT t asks what the database believed at t — facts learned later are invisible even if they describe earlier times. Both together is the audit query: "on March 1, what did we think March 15 would be?" Times are forgiving: YESTERDAY, TODAY, NOW-7d, 10 DAYS AGO, 'yesterday 2pm CST', ISO dates, RFC3339, or raw UnixMicro. Aggregation, SEARCH, CONTEXT, PROFILE and the topology operators all accept these clauses.

FACTS OF item:100001/store:4001 AS OF '2026-03-15' AS KNOWN AT '2026-03-01'
FACTS OF toy:robot AS OF YESTERDAY
FACTS OF toy:robot AS OF NOW-7d
FACTS OF toy:robot AS OF 'yesterday 2pm CST'
CONTEXT FOR toy:robot AS KNOWN AT '2026-03-01'              -- decision replay
FACTS region, SUM(units) OF sku:* GROUP BY region AS KNOWN AT '2026-03-01'

Causality: WHY, EFFECTS, MATCH#

Causes are first-class links. Add WHY to any FACTS query and each result carries its causal chain; WHY <event-id> DEPTH n traces one event backwards, EFFECTS <event-id> forwards. MATCH finds every causal path between two subject patterns, walking outbound (CAUSES) or inbound (CAUSED BY), optionally restricted by VIA to one link type (TRIGGERED, SUPERSEDES, CORRECTS, DISTRIBUTED_AS, ACTIVATED_BY, ENRICHED_FROM). The HTTP equivalent of a trace is GET /v1/trace?event=<id>&direction=cause|effect.

FACTS OF toy:robot WHY DEPTH 3
WHY 0193fa2e-77c1… DEPTH 6       -- what led to this event
EFFECTS 0193fa2e-77c1…           -- what this event led to
MATCH item:* CAUSES register:* VIA TRIGGERED DEPTH 3
MATCH item:100001/store:4001 CAUSED BY * VIA CORRECTS
MATCH intent:* CAUSES pdt:* DEPTH 5 LIMIT 50

Trust: DISAGREE, PENDING, CONTEXT#

Facets let different systems hold different beliefs about one subject, and reconciliation becomes a query. DISAGREE ON <field> lists subjects whose facets disagree, with a trust-ranked suggested winner. PENDING <facet> OLDER THAN n DAYS finds facts that were distributed but never activated ("wedges"); POST /v1/activate closes one. CONTEXT FOR <subject> returns in one call what an agent needs to reason: current facts, recent history, causal chains, disagreements with a suggested resolution, pending wedges, enrichments, schemas and a confidence summary — rebuildable as of any past moment with AS KNOWN AT.

DISAGREE ON price_cents
PENDING pdt OLDER THAN 21 DAYS
CONTEXT FOR toy:robot
CONTEXT FOR toy:robot AS KNOWN AT '2026-03-01'

Reversible transactions: SNAPSHOT, ROLLBACK, DIFF#

Because nothing is erased, a rollback appends superseding reversion facts that restore each subject to a chosen past point and records the rollback itself as an auditable event. AS OF still sees the pre-rollback world, HISTORY grows rather than shrinks, and a rollback is itself reversible. SNAPSHOT 'name' is a durable fact (it survives the session, unlike SQL SAVEPOINT); DIFF previews the delta first.

SNAPSHOT 'before-import'
DIFF OF toy:* BETWEEN '2026-03-01' AND '2026-03-15'
ROLLBACK                                  -- undo the last commit
ROLLBACK TO SNAPSHOT 'before-import'
ROLLBACK OF toy:* TO '2026-03-15'
Honest scope: there is no interactive multi-statement BEGIN…COMMIT MVCC transaction. Writes are single-fact or batch appends; a /v1/append with several events is atomic within one log.

Aggregates, COUNT DISTINCT and HyperLogLog#

Aggregates run over current facts and respect time travel: COUNT(*) COUNT(f) COUNT(DISTINCT f) APPROX_COUNT_DISTINCT(f) SUM AVG MIN MAX MEDIAN STDDEV LISTAGG. COUNT(DISTINCT) is exact; APPROX_COUNT_DISTINCT uses HyperLogLog (internal/ceql/hll.go) with a fixed ~16 KB of memory and ≈0.8% error regardless of cardinality. MEDIAN, STDDEV (population) and LISTAGG carry the Oracle names.

FACTS facet, COUNT(*), AVG(price_cents), MAX(price_cents)
  OF item:*/store:4001 GROUP BY facet
  HAVING COUNT(*) > 5 AND AVG(price_cents) > 300

FACTS APPROX_COUNT_DISTINCT(region) OF item:*
FACTS MEDIAN(price_cents) OF item:*/store:4001
FACTS facet, LISTAGG(kind) OF item:*/store:4001 GROUP BY facet
FACTS facet, AVG(price_cents) OF item:* AS KNOWN AT NOW-2d GROUP BY facet
Honest limit: aggregates run over current facts, not history. To roll up HISTORY results, export and sum client-side.

Schemas#

Optional, versioned and append-only: DEFINE SCHEMA creates a new version; facts written under v1 stay valid against v1. Types are number string bool any; constraints REQUIRED MIN MAX UNIT; a field can carry a description. Write with SCHEMA <id> to validate — a rejection names the bad field. Over HTTP: POST /v1/schema, GET /v1/schema.

DEFINE SCHEMA price (
  price_cents number REQUIRED MIN 1 UNIT 'cents',
  kind string
) TITLE 'A retail price'
PUT toy:car SET price_cents=300 SCHEMA price   -- validated
SCHEMAS            -- list all (latest versions)
SCHEMA price       -- every version of one
Not today: referential field types (parent ref(item)) and foreign-key constraints are roadmap. The recommended integrity pattern is a CePL procedure gateway — see modeling hierarchies.

Standing queries: WATCH#

A WATCH never finishes: it streams every matching fact the moment it commits. In the dashboard it feeds the LIVE panel; over HTTP it is the GET /v1/watch SSE stream (filterable by facet and type); in the Python SDK it's for e in db.watch(...). Streaming endpoints (/v1/watch, /v1/changes, /v1/log) are exempt from admission limits.

WATCH ALL
WATCH toy:robot
WATCH ALL FACET pdt TYPE DISTRIBUTED
curl -N 'localhost:7771/v1/watch?facet=pdt'

Hybrid search: SEARCH, BM25, vectors, SIMILAR#

SEARCH '<text>' OF <pattern> ranks by Okapi BM25 computed in a single pass in pure Go (internal/ceql/bm25.go) — bi-temporal like everything else. It blends with vectors two ways: SIMILAR TO <event> ALPHA a mixes BM25 with embedding similarity to a reference event (ALPHA 1.0 = pure keyword, 0.0 = pure semantic, default 0.5); and with a local embedder registered, SEARCH embeds the query text itself and blends meaning into the ranking. The final order folds in recency, trust (confidence × provenance) and causal centrality, and every hit returns its signal breakdown. SIMILAR TO <event-id> TOP k MIN score is pure vector search. Without an embedder SEARCH is plain BM25 and never errors. SEARCH also indexes AI-derived text (vision descriptions, summaries).

SEARCH 'late markdown' OF item:* LIMIT 10
SEARCH 'markdown' OF item:* SIMILAR TO 0193fa2e-77c1 ALPHA 0.5
SEARCH 'penny' OF item:* AS KNOWN AT '2026-03-01'
SIMILAR TO 0193fa2e-77c1… TOP 5 MIN 0.7
curl 'localhost:7771/v1/similar?event_id=<id>&k=5&min_score=0.7'

Topology: SHAPE, CONSISTENCY, CYCLES, DRIFT#

Four stdlib-only operators (internal/ceql/topology.go) answer questions about the shape of data. SHAPE OF <pattern> ON <fields> computes persistent homology of a value cloud (Betti-0 clusters, Betti-1 loops, Betti-2 voids with MAXDIM 2); WINDOW n STRIDE m builds a time-delay embedding so a periodic signal becomes a loop; ON EMBEDDING METRIC cosine analyses stored vectors. CONSISTENCY OF <subject> ON <field> [EPS n] treats the facets observing a subject as a sheaf: a global section exists iff they agree. CYCLES finds H1 of the causal graph — lineage must be acyclic, so any cycle is a data-integrity alarm. DRIFT … BUCKETS n is a regime-change detector. All accept AS OF / AS KNOWN AT.

SHAPE OF item:*/store:4001 ON price_cents
SHAPE OF item:* ON price_cents, trust, av_cost MAXDIM 2
SHAPE OF item:100001/store:4001 ON price_cents WINDOW 12 STRIDE 2
SHAPE OF item:* ON EMBEDDING METRIC cosine
CONSISTENCY OF item:100001/store:4001 ON price_cents EPS 5
CYCLES IN CAUSES OF item:100001/store:4001
DRIFT OF item:*/store:4001 ON price_cents BUCKETS 6

Modeling hierarchies without foreign keys#

Nodes are subjects and parent pointers are ordinary facts, so a hierarchy is bi-temporal: a reclass is one PUT, and January reports re-run under January's hierarchy. Denormalize ancestry onto leaf facts (dept, class, region) so roll-ups are one GROUP BY that time-travels. Facets carry each system's belief about a leaf, so DISAGREE and PENDING replace reconciliation batches. Integrity is schemas plus CePL procedure gateways: applications call procedures; only admins use raw PUT. Full write-up: docs/modeling-hierarchies.md.

PUT class:3204       SET name='Slim Fit',   parent='dept:320'
PUT sku:100001-RED-32/store:4001 FACET source
  SET units=12, cost_cents=900, price_cents=1999,
      dept='dept:320', class='class:3204', region='region:4'
  SCHEMA sku_loc_status
FACTS dept, SUM(units), AVG(price_cents) OF sku:* GROUP BY dept
FACTS OF class:3204 AS OF '2026-01-15'     -- which dept was it in, in January?

Operations: PROFILE, SUBJECTS, STATS, EXPLAIN#

PROFILE OF <pattern> describes the data (fields, types, coverage, ranges, top values) as of any moment. SUBJECTS LIKE … LIMIT n lists subjects; STATS returns store counters. EXPLAIN <query> returns the access path plus the JSON AST without running; EXPLAIN ANALYZE runs it and reports rows and timing (reads only). Agents can submit the JSON AST directly to /v1/query — also the escape hatch for strings that can't be embedded in CeQL literals, which have no escapes.

PROFILE OF item:*
PROFILE OF item:* AS KNOWN AT '2026-03-01'
SUBJECTS LIKE item:*4001 LIMIT 50
STATS
EXPLAIN FACTS OF toy:robot WHY
EXPLAIN ANALYZE FACTS OF item:*

Lean read-only SQL at /v1/sql#

For people and LLMs who think in SELECT, a lean SQL subset (internal/ceql/sql.go) transpiles to CeQL and runs through the same executor (GET /v1/sql?q= or POST /v1/sql {"q"}; Studio auto-routes SQL). Supported: SELECT * | col, AGG(col) with COUNT SUM AVG MIN MAX; FROM <name> maps to namespace <name>:*, FROM facts to all subjects, a quoted FROM 'item:1' to an exact subject or pattern; WHERE with = != <> < <= > >= IN LIKE AND OR NOT (); GROUP BY, HAVING, ORDER BY, LIMIT n [OFFSET m]; time travel with AS OF / AS KNOWN AT, with SQL:2011 FOR SYSTEM_TIME AS OF as a synonym. It rejects what it doesn't support rather than mis-answering.

SELECT * FROM sku WHERE category = 'beverage' AND price_cents > 1000 ORDER BY price_cents DESC LIMIT 5
SELECT category, AVG(price_cents) FROM facts GROUP BY category HAVING COUNT(*) > 3
SELECT * FROM 'item:1' FOR SYSTEM_TIME AS OF 'yesterday'
curl "localhost:7771/v1/sql?q=SELECT%20*%20FROM%20sku%20LIMIT%2010"
curl -X POST localhost:7771/v1/sql -H 'content-type: application/json' \
  -d '{"q": "SELECT category, COUNT(*) FROM facts GROUP BY category"}'
What SQL is NOT here: read-only — only SELECT; writes use CeQL. No joins (in SQL or CeQL), no subqueries, no window functions, no SQL COUNT(DISTINCT) yet.

CePL stored procedures#

CePL (internal/proc) is a deliberately tiny near-English language inside the database: a procedure is stored as a versioned proc:<name> fact, run by name, and every run returns a step-by-step trace. Statements: PROCEDURE name(p1, p2) … END, LET x = FIRST FACTS OF … (binds a CeQL read), LET y = <expression>, WHEN <guard>: <step> (IS MISSING / IS PRESENT), PUT / CORRECT / RETIRE with ${var} holes, FAIL 'msg', RETURN value. Substitution is injection-safe: templates are re-parsed as CeQL after filling, numbers render bare, a string glued to a word accepts only token-safe characters and never *, and anything else becomes a quoted literal. HISTORY OF proc:x shows every version; writes carry REF 'proc:x' lineage; every stored procedure is auto-exposed over MCP as a typed proc_<name> tool.

PROCEDURE duty_estimate(item, units)
  LET rate = FIRST FACTS OF hts:${item} FACET assess
  WHEN rate IS MISSING: FAIL 'no duty rate on file for ${item}'
  LET cost = FIRST FACTS OF cost:${item}
  WHEN cost IS MISSING: FAIL 'no average cost for ${item}'
  LET duty = cost.av_cost * units * rate.comp_rate
  PUT duty:${item} SET duty_amt=${duty}, units=${units} REF 'proc:duty_estimate'
  RETURN duty
END
# define (admin): body is {"source": "<procedure text>"}

Enterprise storage, HA & the API/LLM gateway

The hash chain: verify, backup, doctor#

The store is an append-only JSONL log with in-memory indexes (internal/store). On open it replays the log (shortcut by centauri.checkpoint); -checkpoint-every N seconds writes that recovery checkpoint while serving so a crash replays only seconds of tail. Every committed line is covered by a per-line SHA-256 chain (integrity.go). centauri verify recomputes it and prints the chain head — record it somewhere external; a future verify reproducing it proves the history is byte-for-byte intact. backup copies the committed log (safe while serving) and verifies the copy's chain head equals the source's. -lazy keeps payloads on disk so data can exceed RAM while the index still fits.

centauri verify -data my.log
centauri backup -data my.log -to backups/my-2026-10-28.log
centauri doctor -data my.log
centauri serve -data my.log -checkpoint-every 30 -lazy

Tablespaces: archives, sealed segments, Merkle roots#

centauri archive -to <dir> seals a log into compressed (typically 5–10×), tamper-evident segments plus a manifest.json. Each segment carries a Merkle root (internal/segment/merkle.go; O(log n) inclusion proofs) and zone maps (min/max times, namespace prefixes, field stats) so queries skip segments that can't match; stats and chain heads stay uncompressed in the manifest, so pruning and verify need no decompression. Serving an archive dir replays sealed segments plus an appendable tail; -auto-seal-mb N seals the tail once it passes N MB (Oracle-style log switch) and centauri seal does it by hand, crash-safe via one atomic manifest switch. compact merges consecutive segments offline without erasing. verify -fast scrubs per-segment Merkle roots in parallel. Sealed segments support per-segment AES-256-GCM crypto-erasure — destroy the key, keep the chain.

data/

  segments/
    00000001.log             # sealed, immutable
    current.log              # the open, appendable tail
  centauri.checkpoint

centauri serve -data mydb-archive -auto-seal-mb 256

Write scaling: group commit and sharding#

Writes are single-writer per log by design — the per-line hash chain is sequential. Two levers: -group-commit coalesces concurrent appends into one fsync per batch on a single chain; serve -shards N (with -data a directory) partitions subjects across N independent shard logs by FNV-1a hash of the subject — each its own chain, lock and committer — written in parallel (~N× throughput). Routed: /v1/append, /v1/current, /v1/history, /v1/asof, /v1/subjects (union), /v1/shards, /v1/query for a concrete subject, and fan-out (internal/ceql/fanout.go) for wildcard FACTS/HISTORY/SEARCH.

HA failover and leader election#

Split-brain is prevented by a monotonic epoch fencing token plus self-fencing: a primary stops accepting writes the instant it can't confirm a live lease. GET /v1/ha reports role/epoch/leader. The bundled lease store uses atomic O_EXCL creation on a shared POSIX filesystem (NFS / EBS multi-attach / k8s shared volume); for multi-AZ without shared storage, plug in any CAS-capable LeaseStore (one interface, two methods).

Replication: follow, sync, merge#

centauri follow -primary <url> keeps a live read-only replica by polling GET /v1/log and ingesting raw bytes, so the follower's hash chain is byte-identical to the primary's; add -addr to serve a read-only API from it. centauri sync -primary <peer> is bidirectional, record-level and echo-safe: it pulls the peer's /v1/changes from a per-peer replication slot, ingests facts it doesn't hold (dedup by event id), and advances the slot — run it on both ends. Multi-master on the same subject converges because "current" is a deterministic function of the facts. merge produces one canonical re-chained log offline.

Honest scope: sync promises the same set of facts, not byte-identical logs. Push mode / pairing and a browser replica are not built.

Retention and legal holds#

centauri retention -pattern '<glob>' -older-than N (internal/retention) previews which subjects would be retired — dry-run by default; -apply RETIREs them by appending retired:true corrections so queries skip stale facts. History is kept, the chain stays intact, and the log does not shrink. A hold:<name> fact with a subject pattern places matching subjects under a legal hold that retention skips — and the engine enforces it: any RETIRE of a held subject is rejected on every originating write path (CeQL, raw append, sharded) until the hold is lifted; replication is exempt so replicas mirror the primary.

centauri retention -data gateway.log -pattern 'gw:*' -older-than 30          # dry-run plan
centauri retention -data gateway.log -pattern 'gw:*' -older-than 30 -apply   # RETIRE
PUT hold:litigation-2026 SET pattern='order:2025-*', active=true
RETIRE hold:litigation-2026                        -- lift the hold
Not yet: a stored-policy scheduler inside the binary (schedule the -apply form externally) and a crypto-erase retention action.

TLS, admission control, structured logs, probes#

-tls-cert/-tls-key terminate HTTPS natively on serve, desktop, -lazy-index and the gateway's proxy listener — no reverse proxy required (Caddy/nginx in front is fine; bind to localhost if so). The gateway: routes and keys as facts#

centauri gateway (internal/gateway, stdlib httputil) turns a Centauri log into a reverse proxy whose entire control plane — routes, API keys, request audit — lives in the database as facts. Config therefore time-travels (AS OF, AS KNOWN AT, HISTORY OF route:api) and the audit is hash-chained and verify-able. Data plane default :8080; -admin :7771 serves the normal dashboard/API over the same store; -admin-inline serves it on the proxy port for unmatched paths (single-port deploys). A route is the current fact of route:<name> facet config; a key is gwkey:<sha256> (the plaintext is printed once and never stored). Mint keys offline with -newkey <name> or live in the Console (/console → Keys & Access).

Gateway auth modes: key, OIDC, mTLS#

auth='key' requires a minted gateway key as a bearer token. auth='oidc' validates the caller's JWT with the same verifier serve uses, forwards X-Auth-Subject: <sub> (any client-supplied value of that header is stripped), and records the JWT sub as the audit key; the bearer passes through to the upstream unless you add "remove_request_headers": ["Authorization"]. -mtls-ca <pem> (mtls.go, with -tls-cert/-tls-key) requires every connection on the proxy listener to present a client certificate signed by that CA — requests without one die at the TLS handshake; the cert CN becomes the audit key when nothing else named the caller. Listener-wide, not per-route.

PUT route:api FACET config SET prefix='/api/', upstream='http://127.0.0.1:9000', auth='oidc', oidc_issuer='https://login.example.com', oidc_audience='my-api'
centauri gateway -data gateway.log -tls-cert srv.pem -tls-key srv.key -mtls-ca clients-ca.pem

Token issuer: POST /gw/token (client-credentials only)#

The gateway can issue short-lived service tokens so machine callers pass auth='oidc' routes without an external IdP (issuer.go). Every gateway key doubles as an OAuth2 client: client_id is the key's name, client_secret is the key. The token is an RS256 JWT with iss = -issuer, sub = key name, aud = -token-aud (default centauri), exp after -token-ttl seconds (default 900), signed by an RSA-2048 key generated on first use and stored as PEM next to the log (issuer.key, mode 0600) — never in the log, because the log can never erase it. The public half is served at /.well-known/jwks.json and /.well-known/openid-configuration. Every issuance and failure is audited on gw:_tokens. RETIRE gwkey:… stops new tokens immediately; issued ones live out their TTL.

Rate limits, CePL request policies, webhook authorization#

Rate limiting (ratelimit.go) is per route (rate_per_min) and per key on top. For programmable logic a route names a stored CePL procedure in policy (policy.go); it runs after auth, rate limit and built-in middleware, immediately before proxying, receiving any subset of method, path, key (resolved caller name, or '' when anonymous) and ip. Its RETURN decides: 'allow'/true proceeds; 'deny'/'deny:<message>'/false is 403; a record is honoured as {"allow", "status", "message", "add_headers"}; anything else, a runtime error, or FAIL is 403 fail-closed. Policies are parsed once per config load and hot-reload when the procedure fact changes; denials are audited even on audit:'none' routes. Measured cost ≈2 µs per request. authz_webhook POSTs {method, path, key, ip, headers} (safe subset only, never the credential) to your service; anything but 2xx, or the 2-second timeout, is 403 fail-closed unless webhook_fail_open.

PUT route:api FACET config SET prefix='/api/', upstream='http://127.0.0.1:9000', auth='key', policy='office_rules'
PROCEDURE office_rules(method, path, key, ip)
  -- writes only from the ci key; reads for everyone
  WHEN method != 'GET' AND key != 'ci': RETURN 'deny:only ci may write here'
  RETURN 'allow'
END
PUT route:api FACET config SET prefix='/api/', upstream='http://127.0.0.1:9000', auth='key', authz_webhook='https://authz.internal/check'
Honest scope: CePL policies are guards plus CeQL reads/writes — no loops, no body access, no request transformation. A plugin marketplace: no.

LLM routing, streaming and token accounting#

Set llm: true and a providers list (llm.go); the gateway speaks the OpenAI-compatible chat-completions shape and fails over in order on unreachable or 5xx providers. Secrets never live in facts: auth_env names an env var, auth_file a key file; local servers like Ollama are keyless. Audit, metrics, retention and scale-out#

With audit: "meta" each request appends a fact on subject gw:<route> facet gateway (audit.go) carrying method, path, status, ms, key (name, never the secret), upstream, bytes_out, and for LLM routes model and token counts — bodies are never recorded. FACTS OF gw:* is the latest request per route; HISTORY OF gw:<route> is the full log. /metrics is on the admin plane. Audit grows the log: retire old audit facts with centauri retention -pattern 'gw:*', or set audit: 'none' on hot routes. Scale-out: run N gateways with -control-follow https://primary:7771 -control-token …; each follows the primary's control log read-only and writes audit to its own local log (-audit-data).

HISTORY OF gw:chat FACET gateway ORDER BY recorded DESC LIMIT 100
HISTORY OF gw:chat WHERE status >= 500          -- every 5xx, forever
FACTS OF route:api FACET config AS OF 5 minutes ago

centauri verify -data gateway.log

Gateway flags: -data (default gateway.log), -addr (:8080), -admin, -admin-inline, -token, -read-token, -tls-cert, -tls-key, -mtls-ca, -control-follow, -control-token, -audit-data, -newkey, -issuer, -token-ttl (900), -token-aud (centauri).

Honest limits: the control plane stays single-writer with no leader election; no cross-gateway audit merge; no multi-DC; not a Kubernetes ingress controller; ~26k req/s measured on a 2-core dev VM — NGINX and Kong still win at the edge. See the gateway comparison.

What Centauri does NOT do

Every line below is stated in the repository docs. Comparison tables say what Centauri does not do, and a ✗ is never inflated to a ✓.

Query & data model

  • Not a general SQL database. The SQL surface is a read-only SELECT subset; writes use CeQL.
  • No JOINs — in SQL or CeQL. No subqueries, window functions, or SQL COUNT(DISTINCT) yet.
  • The Postgres wire listener returns every column as TEXT, authenticates with the token as a cleartext password, has no ?db= routing, and rejects non-SELECT.
  • No multi-statement BEGIN…COMMIT MVCC transactions. No foreign-key constraints (ref types are roadmap). No cost-based optimizer.
  • CeQL aggregates run over current facts, not history. CeQL strings have no escapes — use the JSON AST for awkward values.

Write path & scale

  • Single writer per log. Sharded writes, read replicas and HA failover exist; multi-writer clustering and high-contention multi-writer OLTP do not.
  • Sharded mode: no cross-shard atomic transactions, causal links/trace, or aggregates.
  • The working set lives in RAM; the tablespace/archive tier serves bigger-than-memory data read-only, with no persisted index for arbitrary cold WHERE; vector similarity and causal weighting need the in-RAM index.
  • Object store: read-only cold tier; writes and sealing still target local disk; GCS/Azure signers are design-only.
  • Sync: no push mode/pairing, no browser/edge replica; sync promises the same set of facts, not byte-identical logs.

Security & operations

  • No Vault / KMS / cloud Secrets Manager integration — secrets are env vars or a 0600 key file.
  • At-rest encryption covers sealed segments only; the hot tail, manifest and checkpoint are not encrypted — use disk/volume encryption. End-to-end encryption of the live log is planned.
  • No hot certificate reload; no mTLS on serve (gateway proxy listener only); no OpenTelemetry trace spans.
  • OIDC validates the IdP's tokens; Centauri is not an identity provider for people. No role hierarchies, LDAP/SAML, or claim-to-ACL mapping.
  • Retention RETIREs — the log file never shrinks. No in-binary policy scheduler and no crypto-erase retention action yet.
  • centauri verify proves integrity only against an externally recorded chain head.

AI

  • The engine bundles no model; AI features orchestrate an external runtime (Ollama) and an external PDF renderer — optional add-ons, not built in.
  • GLM-5.2 is cloud-only (200+ GB weights), off by default, sends prompts and retrieved facts off-machine, and costs money. Local tiers top out at glm-4.7-flash.
  • Without a chat model, ASK answers only from kb:* facts and logs gaps — it does not guess. Without an embedder, SEARCH is pure BM25.
  • "Learning" means accumulating facts, not retraining weights. No drag-and-drop spreadsheet import for non-technical users yet.

Gateway

  • Not a Kubernetes ingress controller. Not a plugin ecosystem — a fixed middleware set plus CePL policies and webhook callouts; no third-party plugin API or marketplace.
  • CePL policies cannot transform requests or responses. Token issuing is client_credentials only.
  • The control plane is single-writer with no leader election; no cross-gateway audit merge; no multi-DC; no commercial support.
  • ~26k req/s on a 2-core dev VM; NGINX and Kong still win at the edge. SSE failover applies only until the first byte. Bodies are never recorded in audit facts.
